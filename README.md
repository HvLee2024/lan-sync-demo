# 局域网实时同步 Demo（分层同步）

> **一句话**：逻辑上一份文件，物理上多份副本；写入永不阻塞，稳定之后各端完全一致。
> 稳定之前的分叉被完整保留（操作时间线），但"谁生效"由一条**固定、确定**的规则决定。

这是一个最小可运行的 Web 应用：一台机器当服务端，局域网内任意多台设备用浏览器打开同一个地址，
就能看到**双向实时同步**。服务端承担"实时同步中的异步次序处理"——保留真实操作顺序，
并用确定性规则裁决并发。

当前版本**只做文字同步，不做手写笔迹**，目的是先把同步内核与"分层呈现"跑通。

- **零第三方依赖**：只用 Node 内置模块，不需要 `npm install`
- **测试**：6 个测试文件、84 项断言 + 200 轮抗乱序压力诊断
- **可以当内嵌服务端**：排列顺序由创建键派生，任何一端都能独立算出同一顺序，
  因此"每台设备各跑一个服务端"不会分叉

## 1. 启动

需要 **Node.js 18+**（零第三方依赖，不需要 `npm install`）：

```bash
cd lan-sync-demo

./start.sh                            # 默认端口 8787，权限密码 1111
./start.sh --port 9000                # 换端口
./start.sh --passcode 你的密码         # 换权限密码
```

也可以直接调用：

```bash
node server.js --port 8787 --passcode 1111
```

启动后终端会打印本机地址和**局域网地址**，例如：

```
本机访问 : http://localhost:8787
局域网   : http://192.168.1.10:8787      ← 换成终端实际打印的地址

权限密码 : 1111
```

在**同一局域网的手机 / 平板 / 另一台电脑**上打开那个 `192.168.x.x` 地址，
输入权限密码 **1111**，再给自己的设备起个名字（例如"客厅笔记本"、"我的平板"），即可进入。

> 设备名和标识存在浏览器 localStorage 里，同一个浏览器只算一台设备。
> 想在一台电脑上模拟两台设备，开一个普通窗口 + 一个无痕窗口即可。

## 2. 怎么演示给别人看

按这个顺序演示，效果最好：

**第 1 步：证明"真实时同步"**

- 电脑上打一句话 → 平板上**立刻**出现（同一页，左边的色条标明来源设备）
- 平板上打一句 → 电脑上立刻出现

**第 2 步：证明"逻辑上一份文件"**

点右上角 **`同步校验`**。两端和侧栏都会显示：

```
本端   hash a3f9c1d2e4b50678
服务端 hash a3f9c1d2e4b50678
✓ 一致 —— 本端与服务端状态逐字节相同
```

**两边哈希相同 = 两个副本已经收敛到完全一致。** 这是可验证的一致性，不是"看起来一样"。

**第 3 步：证明"稳定之前允许分叉"**

切到 **`分层视图`**。同一个文件按来源设备拆成独立的层，每层都是一块完整内容，
不会被合并函数切碎重排。这就是"每台设备的输入独立显示、可重叠查看"。

**第 4 步：证明"并发裁决是确定的"**

点 **`并发竞态演示`**。它会向同一分段乱序投递 3 次不同逻辑时钟的修改。
右侧 **`操作时间线`** 会显示：

- **✓ 生效** 的那一次（逻辑时钟最大的）
- **✕ 被并发裁决** 的那几次（划掉，但仍然留在时间线上）

**关键点：落败的操作没有消失，它被记下来了。** 这就是"冲突不作为备份丢弃，而是并存保留"。

**第 5 步：做一次真实的一致性测试**

在两台设备上**同时**输入（同一分段）。你会看到：

- 两边的输入**立刻**在本地出现，谁都不用等谁
- 稳定之后两边都变成同一个结果，哈希一致

**这正是"用户拿同时写入来检验你是不是真实时同步"的场景。**

│  设备 A       │   │  设备 B       │   │  设备 C       │

│              │   │              │   │              │
│ 本地立即生效  │   │ 本地立即生效  │   │ 本地立即生效  │
└──────┬───────┘   └──────┬───────┘   └──────┬───────┘
       │  WebSocket 增量操作                 │
       └──────────────┬──────────────────────┘
                      ▼
        ┌─────────────────────────────┐
        │        服务端                │
        │  只做"机械一致性"：           │

这样云端部署时不需要 `npm install`，也不会有依赖漏洞。

## 4. 数据模型

### 一份"逻辑文件" = 一串分段（segment）

```js
{
  id,              // 全局唯一
  createLamport,   // 创建键之一 —— **排列顺序的唯一依据**，创建后永不改变
  createDevice,    // 创建键之二
  seq,             // 展示用序号（按派生顺序数出来的名次），不参与任何裁决
  deviceId,        // 最后一次写入的来源设备（用于色条与分层）
  text,            // 内容
  lamport,         // 最后一次写入的逻辑时钟
  wLamport,        // 写入裁决键（与展示字段分开，单调不减）
  wDevice,
  dmLamport,       // 删除裁决键（与写入键分开保存）
  dmDevice,
  deleted,         // 墓碑：对外隐藏、对内保留
  rev,             // 版本号，仅用于界面展示
}
```

### 排列顺序：由创建键派生，不由"谁先到"决定

```
排列顺序 = (createLamport, createDevice, id) 的字典序
```

**这是"每一端都能当服务器"能否成立的分水岭。**
如果顺序由服务端到达顺序决定（先到先排），那么当每台设备都内嵌一个服务器时：

- A 的内嵌服务器给某段分配 `seq=5`
- B 的内嵌服务器同时给它分配 `seq=3`
- **两个服务器给出不同顺序 → 不收敛**

改成从创建键派生之后，顺序是一个**纯函数**：任何服务器、任何副本，
只要看到同一组操作，就算出完全相同的顺序。**不需要任何权威服务器来"定序"，
离线设备自己也能算出正确顺序** —— 这正是"不要因为没有公网就放弃同步策略"的前提。

**已知取舍**：派生顺序只保证"追加"语义。要支持"插到任意位置"，
需要把锚点改成确定性的位置引用（我们已把 `anchorId` 保存下来备用，但当前不参与排序）。

### 两条不变量（只依赖操作集合，与投递顺序无关）

```
可见内容 = 键最大的那次【写入】的内容
是否删除 = 键最大的那次【删除】 是否比 键最大的那次【写入】 更大
```

**这两条是整个系统能收敛的全部秘密。** 服务端每次应用操作后都按这两条重算，
而不是在某个分支里"顺手"改标志位。

### 裁决键的比较规则

```
比较 (lamport, deviceId) 这个有序对：
  先比 lamport，相等再比 deviceId（字典序大的胜出）
```

**规则本身是什么不重要，重要的是它固定。** 它不解释任何用户意图。
服务端**绝不**重新生成或放大这个键——一旦用"到达顺序"去放大它，
到达顺序就会渗进裁决，系统立刻不收敛（这一点在开发中被测试抓到过，见第 7 节）。

## 5. 服务端在"实时同步的异步特征"里到底做什么

这是本项目最核心的问题。答案是：**做机械一致性，不做语义一致性。**

| 服务端做的事 | 服务端不做的事 |
|---|---|
| 保留真实操作顺序（`ops` 时间线，含未生效的操作） | 不解释用户意图 |
| 按派生顺序给分段编号（纯函数，任何端都能算） | 不用"谁先到"来定序 |
| 按 `(lamport, deviceId)` 做确定性裁决 | 不生成、不放大操作的逻辑时钟 |
| 计算并广播权威哈希（供各端校验） | 不因并发而阻塞、排队或加锁任何写入 |
| 记录每个分段的**来源设备** | 不隐藏任何被裁决掉的操作 |

**写入永不阻塞**：客户端先在本地应用操作，再异步投递；
断线时进入 `outbox` 队列，重连后按序重放。

**"稳定"的定义**：所有活跃副本都收到了全部操作。
在界面上表现为——两端的 `同步校验` 哈希相同。

## 6. 已知取舍（重要，别当成 bug）

这几条是刻意的设计选择，都写在内核注释里：

**① 墓碑残留内容不进收敛契约。**
墓碑上的 `deletedText`（"这一段被删掉时里面是什么"）只是展示痕迹。
原因是本质性的：**「保留被裁决掉的旧内容」与「纯确定性裁决」无法同时严格成立**——
"哪一次写入被裁决掉"本身就依赖到达顺序。
既然最终一致性是硬要求，就让墓碑内容退化为显示痕迹；
**完整历史由操作时间线无损保留，一条都不少。**

**② 目标尚未创建时，早到的修改会被忽略。**
如果一次 `update` 在它的 `create` 之前到达，这次修改会被静默丢弃（但记入时间线）。
取舍是：宁可丢一次并发修改，也不制造"幽灵分段"。
在真实系统里这个窗口几乎不存在，因为同一设备的操作走同一条 TCP 连接、天然保序。

**③ 逻辑时钟不能太小。**
如果一台设备带着很小的 `lamport` 回来（例如长时间离线后又改系统时间），
它的编辑会被裁决掉。客户端用 `winningKey()` 跟随已知最大键来避免这一点，
但**没有**做逻辑时钟的持久化与重放保护——真实产品需要。

**④ 分段是最小单元，不是字符。**
本 Demo 不支持"两个人同时改同一段的同一句话"的字符级合并。
这符合产品设计：**保持结构，而不是压平后再排序。**
手写笔迹天然是独立对象，不存在这个问题——这也是为什么选"手写笔记"作为产品形态更合适。

## 7. 测试：为什么这套东西必须测

**同步逻辑写错通常不会崩溃、不会报错 —— 它只是让两端悄悄不一致，
而且在用户积累了几百篇笔记之后才被发现。**

所以这里有专门的性质测试。开发过程中它们真的抓到了 5 个 bug：

| 抓到的 bug | 后果 | 修法 |
|---|---|---|
| 服务端把"到达顺序"混进逻辑时钟 | 裁决依赖投递顺序，完全不收敛 | 逻辑时钟由客户端生成，服务端只比较 |
| `rev` 计数器进了哈希 | "内容已一致"被误判成"不收敛" | 从哈希中移除顺序相关的计数器 |
| 删除把 `seg.lamport` 覆盖掉 | 晚到的合法写入被误判为"更旧"而丢弃，可见文本不一致 | 写入键与删除键分开保存（`wLamport` / `dmLamport`） |
| 写入时无条件 `deleted = false` | 先到的删除被错误抹掉，可见性依赖到达顺序 | 每次应用操作后按"最大写入键 vs 最大删除键"**重算**可见性 |
| 服务端调用 `mergeLamport` 改写了投递进来的操作对象 | 又一次把到达顺序渗进裁决 | 删掉这次调用，逻辑时钟只在客户端推进 |
| `renderMerged()` 开头写了 `list.innerHTML = ''` | **每次同步补丁到达都销毁正在编辑的 contenteditable 节点 → 焦点丢失、手机上软键盘收起** | 改为按 id 增量对齐节点，绝不清空容器；并加光标保存/恢复兜底 |

跑测试：

```bash
bash test/run-all.sh               # 全部：共 84 项断言 + 抗乱序压力诊断

# 或单独跑
NODE=${NODE:-node}
$NODE test/hash-parity.test.js     # 两端哈希实现逐字节一致：10 项
$NODE test/focus.test.js           # 焦点保护（同步不抢键盘）：17 项
$NODE test/multi-server.test.js    # 多服务器顺序一致性：9 项
$NODE test/convergence.test.js     # 收敛性质测试：16 项
$NODE test/integration.test.js     # 端到端测试：28 项
$NODE test/diagnose.js 200 500     # 抗乱序压力：200 轮 × 500 操作
```

**`focus.test.js` 这一项也值得单独说**：它用一个极简 DOM 替身，从 `client.js` 里
**直接抽取真实的 `renderMerged` / `buildSegNode` / `updateSegNode` 代码**来跑，
验证"有焦点时渲染，focused 的 contenteditable 节点必须仍在文档内"。
这个 bug 人工很难稳定复现，但一旦复发就是"同步抢键盘"，所以必须自动化守住。

**`hash-parity` 这一项值得单独说**：浏览器端和服务端各自实现了一份 `stateHash`，
两者差一个字节，页面的「同步校验」就会永远显示"不一致"——
**功能从"信任凭证"退化成"永远报警的假警报器"。**
这个测试从 `client.js` 里**直接抽取真实代码**来跑（不是复制一份），所以任何一方被改坏都会失败。

`convergence.test.js` 覆盖 7 组性质：

1. **确定性** —— 同操作 + 同顺序 → 结果逐字节相同
2. **幂等性** —— 同一操作重复投递不改变结果
3. **因果乱序容忍** —— 修改早于创建到达不产生脏数据
4. **大批量收敛** —— 30 轮 × 400 操作 × 3 种乱序投递 → 全部收敛
5. **并发裁决确定性** —— 同一分段的并发修改，先到哪个都不影响最终结果
6. **删除 vs 修改** —— 并发时按同一规则裁决，双向都验证
7. **排列顺序** —— `seq` 唯一连续，锚点插入正确

`integration.test.js` 覆盖整条链路：鉴权（含错误密码/无令牌拒绝）、
双端实时同步、并发竞态、三方哈希一致、墓碑隐藏、时间线保留、**重启后状态不丢**。

## 7.5 输入不被同步打断（设计约束）

这条从最初的对话里就定下来了：**写入永不阻塞**。
但"不阻塞数据"还不够，还必须**不阻塞交互**。做到这一点的三条纪律：

**① 绝不清空编辑区容器。**
任何"重建列表"的渲染都不能用 `innerHTML = ''`。
一旦清空，正在编辑的 `contenteditable` 节点就被移出文档，
焦点与光标一起丢失，手机上键盘会直接收起。
正确做法是按 id 增量对齐：缺的补、多的删、顺序不对的移，**能不动就不动**。

**② 打字期间只做轻量刷新。**
输入事件走 `renderLight()`（只更新哈希与字数），不重建编辑区、不重绘侧栏。

**③ 正在编辑的分段，绝不覆盖其文本。**
用真实的 `document.activeElement` 判断（不用可能过期的标志位）。
远端补丁到达时把新内容记进状态，等失焦后再刷新到 DOM 上。

**兜底**：即使因为别的原因焦点被打断，`renderAll()` 会在渲染前用 `saveCaret()`
记住光标偏移，渲染后用 `restoreCaret()` 恢复。

## 8. 云端部署

服务端是单文件、零依赖，迁移只差三件事：

```bash
# 1) 换端口 + 换密码（务必改掉默认的 1111）
SYNC_PASSCODE='强密码' PORT=8787 node server.js

# 2) 数据落盘位置（默认 ./data/state.json，原子写入）
SYNC_DATA=/var/lib/lansync node server.js
```

**要上的前置项：**

- **反向代理 + TLS**。WebSocket 需要代理转发 `Upgrade`，Nginx 示例：

  ```nginx
  location / {
      proxy_pass http://127.0.0.1:8787;
      proxy_http_version 1.1;
      proxy_set_header Upgrade $http_upgrade;
      proxy_set_header Connection "upgrade";
      proxy_read_timeout 3600s;
  }
  ```

- **令牌持久化**。当前令牌只存在内存里，服务重启后所有客户端需要重新登录
  （本 Demo 会在登录后自动重连，体验上只是重输一次密码）。
  生产环境应改为签名令牌（JWT 或 HMAC），避免重启踢掉所有会话。

- **状态存储**。当前是全量 JSON 落盘（每次改动 400ms 防抖）。
  分段数量到万级时应换成追加日志 + 定期快照，并给 `losers`/时间线做时间分桶淘汰。

- **多进程**。当前是单进程内存状态，只能起一个实例。
  横向扩展需要在前面加一层"文档分区 + 消息总线"。

- **审计与配额**。真实产品需要：按设备/用户记录操作审计、限制单文档体积、
  限制单设备写入频率。

## 9. 下一步（按价值排序）

1. **手写笔迹**。这是产品的本体。笔迹天然是独立对象，"分层"会更自然；
   难点会从"合并语义"转移到**笔迹数据量**（抽稀、曲线拟合、按需降精度、增量传输）。
2. **逻辑时钟持久化**。让设备离线再久回来也能正常写入。
3. **层的生命周期**。什么时候把"层"折叠成公共内容、历史保留多久、如何归档。
4. **主动检验机制**。现在靠"两端点一下校验"；应做成随时可读的稳定状态指示
   （`● 已稳定 / ○ 同步中`），这样用户不必等冲突发生才能验证。
5. **多用户**。一旦有第二个人进来，"层"的标签就要从「我的 iPad」变成「张三的 iPad」，
   需要权限、共享、撤销——复杂度上一个台阶。

## 10. 上传到 GitHub

仓库已经在本地初始化好并完成了提交，只差"创建远程仓库 + 推送"这一步
（这一步只能用你自己的账号授权）：

```bash
./push-to-github.sh              # 公开仓库
./push-to-github.sh --private    # 私有仓库
./push-to-github.sh --no-push    # 只配好远程地址，先不推
```

脚本优先用 `gh` CLI 自动创建仓库并推送。**如果 `gh` 没登录**，它会打印"手动三步"
（网页建仓库 → `git remote add origin ...` → `git push -u origin main`）。

一次性登录（推荐）：

```bash
gh auth login      # 选 GitHub.com → HTTPS → 浏览器登录
./push-to-github.sh
```

## 11. 权限密码

默认 **`1111`**。改法：

```bash
node server.js --passcode '你的密码'
# 或
SYNC_PASSCODE='你的密码' node server.js
```

错误密码会被拒绝（401），未带令牌访问 `/api/state` 同样被拒。
密码比较使用 `crypto.timingSafeEqual`，避免时序侧信道。
